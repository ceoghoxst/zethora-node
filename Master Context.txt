=== SECTION 17: MULTI-CONTEXT LEGO PROTOCOL (SUPERSEDES SINGLE-AGENT READING OF SEC 8) ===
Section 8 defines the loop. Section 17 defines the context separation. Both are required.

17.1 WHY SEPARATION MATTERS
A builder AI that has seen its own code argues for its own code. An attacker AI that has read the builder's reasoning cannot attack freshly â€” it has already accepted the builder's assumptions. The two roles must run in separate chat contexts with no shared history beyond the artifact under test.

17.2 THE THREE CONTEXTS
CONTEXT B (Builder): VS Code + Cline. Writes the feature. Knows the feature spec. Does NOT know the planned attacks. Does NOT write tests intended to break its own code.
CONTEXT A (Attacker / Red Team): Fresh chat. Receives ONLY: the code under test, the interface contract, the security claims. Produces: adversarial test cases that must fail if the code is correct, and pass only if the vulnerability is present. Does NOT propose fixes.
CONTEXT P (Patcher): Same as B or a fresh chat. Receives: failing attack test, the code. Produces: minimal patch. Re-runs the attack test. Re-runs adjacent tests (Blast Radius).

17.3 THE LOOP WITH SEPARATION
  1. B writes feature. B writes positive-control test proving feature works.
  2. Hand off: B produces an artifact bundle (code, interface, claims). No chat history.
  3. A receives the bundle in a fresh chat. A writes adversarial tests. A delivers them as .rs files with assertions.
  4. B or P integrates the attack tests. Run them against current code. Some will fail (vulnerabilities exposed), some will pass (code is safe against that attack).
  5. For each failing attack: P writes a minimal patch. Re-run attack test â€” must turn green. Re-run positive-control â€” must stay green.
  6. FAIL-WHEN-REMOVED proof: P comments out the patch. Attack test must go red again. If it stays green, the attack test is a lie. Restore patch.
  7. BLAST RADIUS: run the full crate's test suite. Adjacent systems must not break.
  8. Merge only when: attack tests green, positive-control green, fail-when-removed proven, blast-radius clean.

17.4 HANDOFF ARTIFACT FORMAT (what B hands to A)
  - The source file(s) under test, verbatim.
  - The public interface (function signatures, HTTP routes, CLI flags, message types).
  - The security claims being made ("this faucet cannot be double-spent", "this search endpoint cannot be DoS'd").
  - The attack surface hypotheses already considered (so A can target the gaps, not retread).
  - NOTHING ELSE. No chat logs, no AI reasoning, no "we tried X and it worked."

17.5 WHAT A MUST NOT DO
  - Must not propose fixes. Attackers attack. If A writes a fix, A has become B and lost the separation.
  - Must not accept "this is probably fine." Every claim is a test target.
  - Must not require reading the builder's chat. If the artifact bundle is incomplete, A requests the missing piece and stops.

17.6 WHAT B MUST NOT DO
  - Must not argue with A's attacks. Run them. If they pass (feature is broken), patch. If they fail (feature is safe), keep the test as regression.
  - Must not soften assertions. If A's test asserts panic on input X, the fix must not turn panic into warn â€” it must not panic on X.
